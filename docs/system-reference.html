01At a glance

The receptionist answers a towing company's phone, collects what the towing team needs, reads it back, and hands the business a lead or a callback over WhatsApp. A rules engine in the backend decides every next step; the voice model only decides how to say it.

flowchart LR
  C((Caller)) -->|phone call| TW[Twilio]
  TW -->|POST /voice /status /after-stream| API["NestJS API, port 3000"]
  TW <-->|WebSocket, 20 ms mu-law frames| GW[Realtime voice gateway]
  GW <-->|wss, audio/pcmu| OAI[OpenAI gpt-realtime-mini]
  GW -->|intake operations| ENG[Intake engine and priority rules]
  ENG <-->|judgments| JEV[TypeSafe Jev]
  ENG --> PG[("Postgres 18, port 5433, RLS")]
  API --> RD[("Redis, live call context")]
  PG -->|lead / callback rows| WA[WhatsApp via Twilio]
  DASH["Angular dashboard, port 4200"] -->|REST + JWT| API
  CF[cloudflared quick tunnel] -.-> API

What it collects

Six required details, asked in this order: what help they need, where the vehicle is (precise enough for a driver to find), the vehicle, whether it can move, their name, and the callback number (the caller ID, confirmed). Destination, condition and notes are saved when offered but never asked for.

The design rules the code keeps

  • The backend decides the next action; the model phrases it.
  • One pinned CALL STATE note before each reply; it replaces the last one.
  • Anything the caller must hear exactly is a fixed line: greeting, read-back, confirmed goodbye, "Are you still there?", the safe fallback.
  • Every word the model speaks is checked live and can be stopped mid-sentence.
  • Never lose a lead: the lead and its WhatsApp row commit in one transaction.
  • Every decision is written to call_events and read back with npm run call:trace.

02One call, end to end

The sequence on the live chatgpt pipeline, from ring to the WhatsApp message.

  1. MILE1
    Ring. Twilio posts /api/telephony/twilio/voice. TwilioSignatureGuard checks the signature against PUBLIC_BASE_URL + the request URL. Throttling is skipped for Twilio (every request shares the tunnel's IP).
  2. MILE2
    Route. The dialled number is looked up in phone_numbers through a narrow RLS escape hatch. An unknown number hears "Sorry, this number isn't set up to take calls right now…" and is hung up on.
  3. MILE3
    Start the call. A calls row is inserted (in_progress), the caller ID seeds the phone slot, CALL_STARTED is logged, and the greeting template is chosen ("Thanks for calling {business}. How can I help?" unless configured) and stored as transcript line 0.
  4. MILE4
    TwiML. <Connect><Stream> to wss://…/api/telephony/twilio/realtime with businessId, callId and an HMAC token, then a <Redirect> to /after-stream for when the stream closes.
  5. MILE5
    Stream admitted. StreamGate checks the token, that the call is live and that the CallSid matches. The greeting and caller number are re-read from the database. The business config loads, the max-call timer arms, and the OpenAI realtime session opens.
  6. MILE6
    Greeting. The model is told "Start the call. Say exactly this and nothing else: …". Audio goes to Twilio in 160-byte frames with a playback mark every 100 ms, so the gateway always knows how much the caller has heard.
  7. MILE7
    Caller speaks. Frames go to OpenAI. On speech onset playback pauses and a loudness gauge decides within 300–1,200 ms whether the caller is taking the floor or just saying "uh-huh".
  8. MILE8
    Turn ends. The gateway asks the backend for the state, pins a CALL STATE note ending in a REQUIRED ACTION, and requests a reply. If no reply audio has arrived 1.1 s later, a filler ("Mm-hm.") plays.
  9. MILE9
    Save, then answer. If the caller gave a detail, the model calls update_call_information. The backend validates, infers, judges the location (Jev, up to 0.8 s) and returns a fresh plan; the model then replies under the new note.
  10. MILE10
    Checked while spoken. Every transcript delta is checked against the guardrails (prices, arrival times, dispatch, AI talk, thinking aloud) and against the plan's DO NOT ASK list. A breach is stopped mid-word.
  11. MILE11
    Judged beside the call. When the caller's transcript arrives, Jev judges danger, urgency, the caller's move, a pending yes, and the service. Nothing waits for it; the results fold in as they land.
  12. MILE12
    Read-back. With everything saved and the number confirmed, the backend sends the read-back as an exact line: "Let me read that back. Your name is Ali, you need a tow, … Is that all correct?"
  13. MILE13
    Yes. The model calls complete_request, or the backend takes the judged yes itself. The call is finalised: a lead (or a callback if something is missing), outcome and duration written.
  14. MILE14
    Goodbye. An ENDING note replaces the last action note, and the confirmed goodbye is said word for word. The line closes once it has played, or after 20 s at most.
  15. MILE15
    Teardown. Transcript lines are flushed, token usage and reply latency are logged (AI_USAGE), and a HANGUP is sent to the backend (a no-op if the call is already finalised).
  16. MILE16
    After the stream. Twilio follows the redirect. If the call failed (a fatal provider error), the caller hears "Sorry, something went wrong on our end…"; otherwise a plain hang-up. The status webhook then confirms completion.
  17. MILE17
    WhatsApp. The lead or callback message, committed with the call, is sent right away and retried by a 5-second sweeper if it fails.

Stream admission

The token is HMAC-SHA256(JWT_ACCESS_SECRET, "twilio-stream:v1\n" + JSON([businessId, callId, callSid])), compared in constant time. The gate also requires the call to be in_progress with a matching CallSid, and replaces the socket's greeting and caller number with the database's. A refused stream is closed and logged ("Refused a stream for call X"); the token has no expiry and is not single-use.

Finalising a call

commitTurn is the only writer. In one tenant transaction it locks the call row FOR UPDATE, writes the transcript, runs the effects (events, lead, callback, WhatsApp rows), and updates the call. If the row is no longer in_progress it only appends the caller's words: this is the finalise-once lock that stops a teardown and the status webhook creating two leads. A partial unique index leads_call_unique backs it up.

A caller turn

  1. input_audio_buffer.committed → the turn counter goes up, any unresolved hold is resumed, and startTurn runs (or the turn is deferred if it was words said over the receptionist).
  2. A reply is now owed: the stall timer starts, and silence is not counted until a reply starts.
  3. The backend's state op returns the plan; a pinned note is built with beforeSave: true ("This state does not include anything from what the caller just said…").
  4. A reply is requested with a number (tag). A reply that starts with a number below supersededBelow was asked for under an old plan and is dropped unheard.
  5. A filler is armed for 1.1 s after the request.

Barge-in: the hold

On every speech onset while the receptionist is speaking, the gateway sends Twilio clear, rewinds each item to what was played, and opens a hold. A SpeechGauge then reads each 20 ms frame: a frame is voiced when its RMS is at least the caller's bar and 2.5× the line's noise floor.

  • Interrupt at 650 ms voiced: cancel the response, truncate the model's memory to what was heard, log AI_INTERRUPTED. A read-back cut short is reported (read_back_cut), and a counted question the caller never heard is taken back (ask_unheard).
  • Resume after 300 ms quiet with less than that: the unheard audio is re-sent, the hold keeps watching, and the next committed turn is treated as an overlap.
  • The caller's bar: 250 RMS by default. VoiceLevel learns each caller's level from frames heard while they speak alone, and lowers the bar to half their usual level, never below 120. Added on 9 October after a soft-spoken caller was talked over with "0 ms voiced".
  • Holds and interruptions log loudestRms and minVoicedRms; the trace prints "loudest X, voice from Y".

Words said over the receptionist

Deferred until playback ends and the words are transcribed (up to 1.5 s). Jev judges whether they answer: ≥ 0.7 answer them, ≤ 0.3 say nothing, anything in between goes to word lists. With word lists, a presence check ("hello?") or a backchannel ("okay", "uh-huh") needs no reply, unless the receptionist had just asked a question, in which case a backchannel may be the answer. Untranscribed words are always answered. Logged as OVERLAP_DECIDED.

Fillers

Seven clips are recorded at start-up in a separate realtime session, out of band, each checked against its transcript and at most 2.5 s long: turn fillers "Mm-hm.", "Okay.", "Right.", "Uh-huh." and stall fillers "One moment.", "Just a moment.", "Bear with me." They are played as synthetic audio, never enter the model's conversation, and stop as soon as real reply audio arrives.

Tool calls

  • Tools run one after another through the call's serial queue; each result updates the active plan.
  • The note sent with the results says what the model already said in that breath, so it carries on instead of repeating.
  • When the plan is CONFIRM_DETAILS, the reply is the read-back as an exact line with tools off.
  • When the model already asked a question in the same breath and the next action is another ask, no second reply is requested: the caller is answering the first.
  • When complete_request ended the call, the confirmed goodbye is said word for word.

Live checks on every word

checkGuardrails runs first on each transcript delta; checkRequiredAction runs only if the guardrails let it through. A guardrail trip stops the reply: trip 1 gets a recovery note, trip 2 the fixed safe line (self-talk gets up to two retellings). A question about a DO NOT ASK topic is stopped once per caller turn and redirected; later ones are only logged as ACTION_DEVIATION.

The backend taking a yes

When Jev judges a caller line a clear yes to a pending question, the backend acts on it itself. A yes to the number confirms the caller ID; a yes to a fully heard, current read-back finishes the call. The gateway then either ends the call with the confirmed goodbye, or re-plans: a reply under way gets replanPending, an owed reply is superseded, and a reply that already asked something is left for the caller to answer.

Ending

beginEnding pins ENDING_NOTE in place of the last action note, starts the 20 s backstop, and from then on drops any reply that is not a goodbye. Caller turns during the goodbye get no reply.

Transcripts and latency

Caller lines are kept in speaking order. A line that is echo, empty or late is dropped with a reason. Every receptionist item is logged as AI_RESPONSE with how much was heard; a stopped line keeps every word, marked [interrupted], [stopped] or [call ended]. Reply latency is measured from the caller's committed turn to the first non-filler audio sent, and summarised at teardown.

Requests and notes

  • One response at a time. A request made while one is active waits in a single queued slot; the latest wins.
  • One-off instructions replace the session instructions for that response only: ${session.instructions}\n\nRIGHT NOW\n${oneOff}.
  • Pinned notes are role: system conversation items. Each new pinned note deletes the previous one, so only the latest state is in context (thirty stale notes once pushed a call past the rate limit and 16 s reply starts).
  • Tool results go back as function_call_output; the snapshot is stripped from them when a note carries it.
  • AI_USAGE at teardown records text, audio and cached tokens and the reply-latency summary. Prices come from REALTIME_PRICE_* if set.

The priority order

The first rule that applies wins. Exact ask texts are in section 8.

  1. CLOSE: the call has ended.
  2. HANDLE_SAFETY: a hazard is known and the advice has not been given (it stays due for the whole turn it is given on). A shoulder stop on a high-speed road gets one short sentence; anything else gets the full line. The emergency number comes from the caller's country code.
  3. CLARIFY_FIELD: a value the model was unsure it heard is checked once.
  4. ASK_SERVICE_TYPE → ASK_LOCATION → ASK_VEHICLE → ASK_VEHICLE_MOVABLE → ASK_CUSTOMER_NAME, in order. A repeat ask gets ASK_AGAIN wording. After 3 caller turns a detail is left for the towing team. A service the judge could narrow to two kinds is offered ("a tow or a jump start?"). A tow caller is asked whether it can roll and steer rather than whether it needs a tow.
  5. ASK_LOCATION_DETAIL: a location too vague to drive to ("I-95") is narrowed before anything lower, at most twice.
  6. Last chance: a detail given up on is asked once more before the read-back, if the caller has since answered something asked after it.
  7. CONFIRM_CALLBACK_NUMBER ("is the number you're calling from the best one?", never read out) or ASK_CALLBACK_NUMBER; given up after 3 turns, the caller ID stands unconfirmed.
  8. CONFIRM_DETAILS: the read-back as an exact line.
  9. AWAIT_CONFIRMATION: wait for a yes without reading the details again (or finish a read-back the caller spoke over, from where they stopped hearing).

doNotAsk is every topic later in the order, plus everything already settled, plus the destination. It appears in each note as DO NOT ASK ABOUT and is enforced live by the response check.

Confirmations

  • A yes only counts on a later caller turn than the question.

ANSWERED_FLOOR0.5Below it, the next note says YOU DID NOT ANSWER THIS
TOPIC_CONFIDENCE_FLOOR0.6ETA or price noted on the lead
SERVICE_CONFIDENCE_FLOOR0.75The judged service is saved, marked inferred
SERVICE_ALTERNATIVE_FLOOR0.15A kind of help is offered as an alternative

What each judgment changes

  • Location precision → a partial location triggers ASK_LOCATION_DETAIL; the note says "(not precise enough yet)"; the lead says it is approximate.
  • Hazard and urgency → HANDLE_SAFETY first; urgency acknowledged once; URGENT on the lead and its WhatsApp heading.
  • Service → saved as inferred at ≥ 0.75, or the two likeliest offered.
  • Confirms / corrects → the backend takes a clear yes itself; a model claim without one is refused.
  • Move and answered → a missed complaint, question or line check is put in the next note, once.
  • Topic → "Caller asked how long / the price" on the lead.
  • Answers (overlap) → whether words said over the receptionist get a reply.

The realtime eval harness

Runs the production gateway against a live OpenAI session with an in-memory backend that uses the real intake rules and Jev. The caller's lines are synthesised (gpt-4o-mini-tts, voice ash) and played at 3× speed; a fake Twilio socket echoes playback marks. realtime:check runs two scenarios once (about 20 s); a full run is 485 runs (30 per targeted scenario, 5 otherwise).
